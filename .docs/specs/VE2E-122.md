# VE2E-122 — Chuyển Script V1 sang Responses API

## Trạng thái

`done` (2026-10-05, chủ dự án xác nhận). Chạy thật ở gate B04 chưa thực hiện lúc xác nhận.

## Bối cảnh

- V00-05 bị VE2E-01 thay thế. Spec V00-05 ghi: chuyển Script V1 sang Responses API phải làm bằng task riêng. Task này là task đó.
- Script V1 là luồng Jobs cũ: `JobsService.generate` → `callContent` → `generateLiveStructured` trong `packages/providers/src/live-content.ts`. Với `openai` và `xai`, luồng này vẫn gọi `/v1/chat/completions`.
- Script V2 (Auto, Studio), trích keyword và probe model đã đi qua `generateContentOnce` → `generateOpenAi` / `generateXai`, tức là gọi `/v1/responses`.

## Phát hiện khi lập spec

1. **Parser Responses API hiện tại đọc sai trường.** `generateOpenAi` và `generateXai` chỉ đọc `body.output_text`. Trường này là thuộc tính tiện ích do SDK tính ở phía client (openai-node, `src/lib/ResponsesParser.ts`, hàm `addOutputText`). JSON thô của REST `/v1/responses` không có nó. Văn bản thật nằm ở `output[]`, trong item `type: "message"`, tại `content[]` part `type: "output_text"`, trường `.text`.
   - Hệ quả dự kiến khi chạy thật với OpenAI: script V2, trích keyword và probe model đều lỗi `PROVIDER_SCHEMA_INVALID` ("OpenAI did not return structured text").
   - Lỗi chưa lộ ra vì 13 chỗ giả lập trong test đều đặt `output_text` ở cấp trên cùng, và gate B04 (chạy thật) chưa chạy.
   - Chưa đối chiếu được dạng response của xAI, nên parser phải nhận cả hai dạng.
   - Nếu chuyển V1 sang các hàm này mà không sửa parser, V1 sẽ hỏng. Hiện V1 vẫn chạy được bằng Chat Completions.
2. **Số token của V1 đang luôn là `null` với OpenAI/xAI.** `usage()` đọc `input_tokens` / `output_tokens`, nhưng Chat Completions trả về `prompt_tokens` / `completion_tokens`. Chuyển sang Responses API sẽ sửa luôn lỗi này.
3. **V1 gửi `temperature: 0.7` kèm system message, V2 không gửi `temperature`.** Các model reasoning (`gpt-5`, dòng `o`) từ chối tham số `temperature` với lỗi HTTP 400.

## Phạm vi

### A. Parser Responses API dùng chung (`live-content.ts`)

- Hàm đọc văn bản từ response (`responsesText`):
  - Ghép `text` của mọi part `type: "output_text"` trong các item `type: "message"` của `output[]` (dạng REST thật).
  - Không có part nào thì dùng `output_text` ở cấp trên nếu đó là string.
- Không có văn bản mà có part `type: "refusal"` → `PROVIDER_CONTENT_REFUSED` (không retry).
- `status: "incomplete"` → `PROVIDER_SCHEMA_INVALID`, message ghi kèm `incomplete_details.reason`.
- Áp dụng cho cả `generateOpenAi` và `generateXai`. Việc này sửa luôn V2, trích keyword và probe.

### B. Script V1 dùng Responses API

- Trong `generateLiveStructuredOnce`, nhánh `openai`/`xai` gọi `/v1/responses` qua `generateOpenAi` / `generateXai` với tham số tuỳ chọn mới. Nhánh `gemini` giữ nguyên.
- System message hiện tại chuyển thành `instructions`, giữ nguyên câu chữ.
- Có schema: `text.format = { type: "json_schema", name: "script_draft_v1", strict: true, schema }`.
- Retry không schema (sau `PROVIDER_SCHEMA_INVALID`): dùng `text.format = { type: "json_object" }`. Cách này giữ hành vi JSON mode của V1; prompt V1 đã có chữ "JSON", đúng yêu cầu của JSON mode.
- Giữ nguyên: retry sang model được gợi ý, phân loại lỗi `fail()`, timeout 120 s.
- Không gửi `temperature` (quyết định 1), giống V2.
- Tham số mới đều là tuỳ chọn. **Request body của V2 (`generateContentOnce`) phải giữ nguyên từng byte**, có test khẳng định.

### Không đổi

`jobs.service.ts` (chữ ký `generateLiveStructured` giữ nguyên), việc ghim `promptTemplateVersion` / `schemaVersion` / `providerConfigVersion`, Gemini, DB và migration, UI.
